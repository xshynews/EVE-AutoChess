# 联机方案

本文说明 EVE 自走棋的联机架构、已做的取舍、实测记录与后续路线。代码入口：

| 层 | 文件 | 职责 |
|---|---|---|
| 房间协调 | `scripts/net/ddz_room.gd` | UI 只和它打交道；串起下面几层 |
| 会话 | `scripts/net/ddz_net.gd` | 房主权威、按座位裁剪快照、掉线托管 |
| 传输 | `scripts/net/eve_ddz_transport.gd` | ENet 收发 |
| 连通 | `scripts/net/eve_tunnel.gd` | 启停内置 EasyTier 内核 |
| 参数派生 | `scripts/net/eve_room_code.gd` | 房间码 → 网络名、密钥、网段、端口 |
| 会合节点 | `scripts/net/eve_relay_list.gd` | 内置的会合 / 中继节点列表 |

## 1. 现状与约束

- 斗地主与自走棋都是回合制，单局流量很小（快照不到 2 KB），对延迟不敏感。
- 局面只存在于房主一侧（房主权威），客户端只收到裁剪后的快照，看不到别人的手牌。
- 连通靠内置的 EasyTier 内核：玩家之间只交换一个 8 位房间码，其余参数都由它派生。
- EasyTier 只解决「连得上」（打洞 + 中继），不解决「找得到人」（房间列表、快速匹配）。

## 2. 连通层：全员 no-TUN

### 结论

房主与加入者都以 `--no-tun` 运行：

- 不创建虚拟网卡，**不需要管理员权限**，也不需要 wintun 驱动；
- 加入者用 `--port-forward` 把本机 `127.0.0.1:27015` 转发到房主的虚拟 IP；
- 房主的内核把收到的流量交给本机端口，游戏服务器**只监听 `127.0.0.1:27015`**，
  不对局域网开放，因此不会触发 Windows 防火墙提示；
- 网络密钥经环境变量 `ET_NETWORK_SECRET` 传给内核，不出现在进程列表的命令行里。

局域网直连（`ddz_room.skip_tunnel = true`）时，服务器仍监听所有网卡。

### 为什么之前认为房主必须建虚拟网卡

早期实测时，房主的游戏服务器绑定的是虚拟 IP。no-TUN 模式下系统里没有这个地址，绑定失败
（`WSAEADDRNOTAVAIL`），于是得出「被连接的一方必须建虚拟网卡」。实际上 EasyTier 文档写明
no-TUN 节点可以经虚拟 IP 被访问（TCP / UDP / ICMP），只是流量由内核交给本机端口，
服务器应监听 `127.0.0.1` 或 `0.0.0.0`，而不是虚拟 IP。

### 实测记录（2026-10-12，EasyTier 2.6.4，Windows 11）

测试 A：两个内核以普通用户权限运行（`runas /trustlevel:0x20000`，并在进程内确认未提权），
加入者经端口转发访问房主。

| 项目 | 结果 |
|---|---|
| 房主服务器绑定虚拟 IP | 失败，`WSAEADDRNOTAVAIL`（即早期结论的来源） |
| 房主服务器监听 `0.0.0.0:27015`，UDP 往返 | 20/20，0.1~1.7 ms |
| 同上，TCP | 成功 |
| Godot ENet 连接 + 10 条可靠消息 | 15 ms 连上，10/10 |
| 房主服务器只监听 `127.0.0.1:27015` | UDP、TCP 均成功 |
| 对照：关闭房主内核后重测 | UDP、TCP、ENet 全部失败（证明流量确实经隧道） |
| 隧道字节计数 | 测试前后增加约 2 KB，与测试流量吻合 |

测试 B：`tools/probe_tunnel_notun.gd`，用游戏自己的 `eve_tunnel` 生成真实参数
（房主 `-i 虚拟IP/24`、加入者 DHCP、全员 no-TUN、密钥走环境变量），
`eve_ddz_transport` 以 `127.0.0.1` 监听，普通用户权限运行。

| 项目 | 结果 |
|---|---|
| 房主内核就绪 | 约 550 ms，无管理员权限请求 |
| 内核实际生效的网络密钥（`easytier-cli node config`） | 与房间码派生值一致 |
| 加入者 DHCP 取址后 ENet 连上房主 | 2~4 s |
| 10 条可靠消息往返 | 10/10 |

另测：内核目录只放 `easytier-core.exe` 与 `Packet.dll` 时，no-TUN 模式可正常启动，
因此发布包不再需要 `wintun.dll` 与 `WinDivert64.sys`。

两项测试都在同一台机器上进行，两个内核经本机局域网 IP 直连。跨网络的打洞与中继路径
此前已由作者实测连通；no-TUN 改变的只是「连通之后数据交给谁」，与网络路径无关。

### 复现

```bash
python tools/pipeline/_fetch_easytier.py
"$GODOT_BIN" --headless --path . -s res://tools/probe_tunnel_notun.gd -- --lan=<本机局域网IP>
```

同机测试时两个内核要经局域网 IP 互连，经 `127.0.0.1` 互连会失败（内核会逐个绑定网卡地址发起连接）。

### 注意

- 房主看到的所有加入者地址都是 `127.0.0.1`（端口不同），不能用 IP 区分玩家，
  要用 ENet 的 peer id（`ddz_room` 已按 peer id 分配座位）。
- 加入者与房主在同一台机器上时，加入者的端口转发与房主的服务器会争用 27015，
  只影响同机调试，探针里把加入者的本地端口改成了 27016。

## 3. 会合与中继节点

- 所有玩家必须连同一份节点列表，否则互相看不到。
- 内置节点都是第三方公益节点，随时可能失效（官方的 `public.easytier.cn` 已于 2026-02 停服）。
- **建议自建一个节点**，部署方法见 `tools/server/easytier-relay/`。用
  `--relay-network-whitelist "eve-ddz-*"` 只为本游戏的房间转发数据。
- 有了大厅服务后，节点列表改为服务器下发、内置列表兜底，换节点不必发新版本。

## 4. 匹配：大厅服务（待做）

EasyTier 没有房间列表与匹配功能。要让匹配好用，需要一个小型大厅服务：

```
房主 ──建房──▶ 大厅 ──房间码──▶ 房主启动内核并监听
加入者 ──快速匹配 / 房间列表 / 输入房间码──▶ 大厅 ──房间码──▶ 加入者启动内核并连接
```

功能：

- 建房、公开房间列表（好友房不公开，只能凭码加入）、快速匹配队列；
- 心跳与房间过期；
- 协议版本校验：只匹配同一协议版本的玩家；
- 下发会合节点列表；
- 邀请链接（例如 `eve://join/<房间码>`）。

实现：先用一个 WebSocket 小服务（Godot 自带 `WebSocketPeer`），与中继节点部署在同一台机器上；
以后需要账号、排位、好友时再评估 Nakama 等现成方案。

## 5. 可靠性要点

| 项目 | 做法 | 状态 |
|---|---|---|
| 防冒充 | 座位由连接身份（peer id）决定，不信任客户端自报 | 已有（`ddz_room`） |
| 手牌隔离 | 每个座位只收到自己的手牌，种子不下发 | 已有 |
| 掉线 | 心跳超时转电脑托管，重连后解除 | 已有 |
| 握手 | 协议版本 + 游戏版本 + 玩家凭证 | 待做 |
| 断线重连 | 凭证 → 重新绑定座位 → 补发完整快照 | 待做 |
| 命令去重 | 命令带序号，重发不重复生效 | 待做 |
| 房主离开 | 本局作废。不做房主迁移：迁移等于把整副牌交给新房主 | 规则 |

**房主作弊**：P2P 房主权威模式下，整副牌在房主电脑上，内存工具可以看到别人的手牌。
娱乐币对局可以接受；如果以后有排位或有价值的输赢，应把房主逻辑放到服务器上运行。
`ddz_net.gd` 是纯逻辑，不依赖 UI 与网络，可以直接放进无头 Godot 服务器。

## 6. 8 人自走棋联机（后续）

回合制同步 + 确定性重放：

1. 每回合房主收集 8 个阵容，下发对阵表与战斗种子；
2. 客户端用同一种子在本地模拟战斗，只用于显示（战斗模拟是固定步长 + 独立随机数）；
3. 胜负以房主结果为准，客户端核对校验值，不一致时以房主为准。

不同 CPU 架构的浮点运算可能有细微差异，所以不能让客户端各自判定胜负。

## 7. 路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| P0 | 全员 no-TUN、服务器只监听本机、密钥走环境变量、自建节点配置 | 本次完成（节点需实际部署） |
| P1 | 大厅服务 + 游戏内大厅界面；握手与断线重连 | 待做 |
| P2 | 服务器模式：同一份 `ddz_net` 跑在服务器上，客户端只向外连服务器；EasyTier 保留为局域网 / 无服务器模式。顺带解决安卓（EasyTier 内核在安卓上无法以子进程方式运行） | 待做 |
