## 一、15 关通关没有通关演出

### 现状（已查实）

通关**有判定**，但**没有任何演出**。战后走的是和普通节点一模一样的结算页，
只有两处不同：

| 位置 | 代码 | 实际效果 |
|---|---|---|
| 标题 | `scripts/ui/panels/eve_result.gd:867` | 「拦截成功」→「遥望边境已肃清」 |
| 按钮 | `eve_result.gd:871` | 「继续 · 下一节点」→「↻ 再来一局」 |

其余全部照旧：信标 −0、击沉数、经验、打捞区。**玩家的主观感受就是"又打了一关"**，
而不是"我通关了"。这是设计缺口，不是 bug。

补充：`scripts/scene/eve_phase_resolve.gd:248 on_run_ended()` 只在日志里追加一行
`═══ 本局结束：通关 · 节点 15／15 ═══`，这行还埋在 172px 宽的日志窗里
（而且大概率被截断，见第二条）。

### 方案：独立的全屏演出层（6.4 秒）

不动结算页的核心逻辑，只加一层 **通关演出**，播完再进结算页。
分镜见对话里的时间轴图。要点：

**为什么是"先演出、后结算"而不是"把结算页做好看点"**

行为心理学上，通关瞬间是多巴胺从波峰回落的关键窗口。这时候直接甩一张
信息密集的结算页，玩家的唤醒度会立刻归零 —— 就是我们现在的样子。
正确节奏是「先成就（纯情绪，0 信息）→ 后统计（数字飞入）」。
参考：喷射战士结算前那 1 秒蓄力停顿、守望先锋的「胜方展示 → 最佳回放 → 点赞 → 个人数据」分段。

**六个阶段**

| 时间 | 阶段 | 画面 | 音频 |
|---|---|---|---|
| 0.0–0.4s | 减速定格 | `Engine.time_scale` 0.3，敌方残骸缓慢解体 | 低频 boom 拖尾 |
| 0.4–1.4s | 镜头后拉压暗 | 环绕相机后退抬高，四周渐黑 | 环境音淡出 |
| 1.4–2.1s | **蓄力静默** | 全黑 + 一条细光带横扫 | **静音**，只留轰鸣 |
| 2.1–3.0s | 标题炸开 | 「边境已肃清」逐字弹出（40ms/字） | 金属撞击 ×4 |
| 3.0–4.6s | 战果飞入 | 击沉 / 存活 / 用时三数飞入 | 轻快点缀 |
| 4.6–6.4s | 收束 | 按钮浮入，音乐推起 | `border_final_01.ogg` |

**工程落地**

| 项 | 做法 |
|---|---|
| 新文件 | `scripts/ui/eve_clear_ceremony.gd`（CanvasLayer，全屏） |
| 触发点 | `eve_phase_resolve.popup()` 里判断 `payload.ending == "cleared"` ⇒ 先播演出，`finished` 信号回来再 `_hud.show_result()` |
| 不触发的情况 | 撤离（`ending == "evacuated"`）、失败、联机对战 —— 一律走原结算页 |
| 跳过 | 演出期间任意点击 / ESC ⇒ 立刻跳到结算页（**必须做**，第 N 次通关的玩家会烦） |
| 音频 | 已有 `assets/audio/music/border_final_01.ogg` 可直接用；撞击音可复用 `boom_04.ogg` 降调 |
| 粒子/光带 | 现有 `eve_battle_fx` 的贴图能拼，不需要新美术 |
| 结算页 | 保留全部战报与打捞，否则玩家会丢掉通关那一局的信息 |

**需要你定的一件事**：标题文案。「边境已肃清」是现在的词，但它是**结算页标题**，
演出里可以用更长一句（比如「第十五节点 · 边境肃清」+ 副标题「本局结束 · 无人生还」）。
这个我按你定的来。

## 二、战斗日志丢信息

### 现状（已实测，不是猜）

写了探针 `tools/probe_log_width.gd`，用**真实字体**量了 12 条生产模板日志：

```
可用宽度 90px（9 号字，约 10 个汉字）
12 条里 10 条被截断 → 截断率 83%
```

明细（节选）：

| 日志 | 文字实宽 | 可用 | 结果 |
|---|---|---|---|
| 系统 战斗开始：6 v 6 | 86px | 90px | ✓ 完整 |
| 损伤 裂谷级 已被摧毁 | 86px | 90px | ✓ 完整 |
| 破层 裂谷级 的护盾被击穿 | 104px | 90px | ✗ 截 14px |
| 后勤 惩罚者级 → 裂谷级 装甲 +12 | 136px | 90px | ✗ 截 46px |
| 结算 结算：击沉 3 艘 · 获得 12 星币 | 143px | 90px | ✗ 截 53px |
| 系统 旗舰 末日沙场级 集火点名：守夜者级 | 170px | 90px | ✗ 截 80px |

**这正是"有时候有有时候没有"的成因**：截断是从**尾部**砍，而数值几乎都在尾部。
船名短（裂谷级 3 字）时「已被摧毁」能露出来；船名长（末日沙场级 5 字）时连后面的词一起没了。
玩家看到的是"同一类信息，有时显示有时不显示"，而不是"明显被截断"——
因为省略号在 172px 的窄栏里不显眼。

### 另外两处（条目级，不是截断）

| 机制 | 位置 | 影响 |
|---|---|---|
| `HIDDEN_CATS = [&"fire"]` | `eve_combat_log.gd:29` | 命中伤害整类不上屏（**是你 10-25 要求的**，别动） |
| `MAX_LINES = 120` | `eve_combat_log.gd:20` | 超过 120 行砍最旧的；一场战斗约 40~60 条，暂不触发 |
| `_entries` 400→300 | `eve_combat_log.gd:112` | 只影响滚动回溯 |

⇒ **主要矛盾是显示截断，不是条目丢失**。

### 方案（按性价比排序）

| # | 手段 | 代价 | 效果 |
|---|---|---|---|
| ① | **模板瘦身**：把数值挪到前面 | 改 6 处 `_log()` 文案 | ★★★★ 立刻见效 |
| ② | 窗口 172 → 208 宽 | 左列要重排（会挤舰队构成） | ★★★ |
| ③ | 字号 9 → 8 | 手机上偏小 | ★★ |
| ④ | 悬停 / 点击展开全文 | 手机没有 hover，要长按 | ★★ |
| ⑤ | 允许 2 行（只在关键类） | 200px 高只放得下 3 条 | ★ |

**推荐 ①+②**。①的具体改法（关键：**尾部必须是可变长信息**，固定信息前置）：

| 现在 | 改后 | 省下 |
|---|---|---|
| `惩罚者级 → 裂谷级 装甲 +12` | `+12 装甲 惩罚者级→裂谷级` | 数值永远不会被截 |
| `裂谷级 的护盾被击穿` | `破 裂谷级·盾` | 5 字 |
| `旗舰 末日沙场级 集火点名：守夜者级` | `集火 末日沙场级→守夜者级` | 4 字 |
| `僵持过久 —— 按剩余战力判定收场` | `僵持 · 按剩余战力判定` | 5 字 |

②的坑：左列纵坐标是 2026-10-13 二修时按「构成 240 + 装备 300 + 增益」硬排的
（`eve_hud_root.gd:552-560`），加宽日志窗会挤压装备栏高度。**需要和第四条的装备面板一起排**。

## 三、电子船偏弱 + TTK 偏长

### 现状（两条独立原因，都查到了出处）

**原因一：电子战船的数值被刻意抹平了。**

`scripts/data/eve_trait_table.gd:83-85` 写着：

> 用户同时把这几艘的**数值归一**了：攻击型的攻击降到同族防御型档位、
> 防御型的血降到攻击型档位 ⇒ 电子战船的战斗力被刻意抹平。

也就是说 8 艘电子战船（`EW_SHIP_KEYS`：小鹰/巨鸟、特里斯坦/狂怒者、伐木者/刺客、刽子手/启示）
**天生比同费用船弱**，只换来一个羁绊位。

**原因二：羁绊效果本身很弱。**

`eve_trait_table.gd:266-275`：敌方开火间隔 +5% / +10% / +15%（阈值 2 / 4 / 6 艘）。

实测（同文件 252-258 行的 A/B 记录，120 局/格）：

| 敌方间隔倍率 | 我挨伤 | 降幅 |
|---|---|---|
| 1.00 | 803 | — |
| 1.05 | 780 | −2.9% |
| 1.10 | 764 | −4.9% |
| 1.15 | 743 | **−7.5%** |

**满档 6 艘电子战，只换来 7.5% 的减伤**。这就是"鸡肋"的量化答案。

### 关键洞察（这条比数值本身重要）

**TTK 缩短会直接削弱电子战。**
电子战的收益是「把敌人的输出摊薄到更长时间轴上」——战斗越长，累积减伤越多。
把 TTK 从 39 秒压到 27 秒，等于把这条羁绊的收益窗口砍掉三成。

⇒ **不能"一边缩短 TTK 一边加强电子战"用同一套数值语言**。
电子战必须从「拖时间」改成「削减输出」或「先手压制」，否则两条需求互相打架。

### TTK 现状（`sim_winrate.gd:44-49` 的实测记录）

```
平均 38.8s · 中位 41.4s · 90% 分位 45.1s · 超时限 1 局
N1 37.7 · N5 44.7 · N8 41.3 · N12 21.6 · BOSS 37.3 · 联机 6v6 43.1
```

常规时限 60s、BOSS 70s ⇒ **当前 TTK 只占时限的 65%**，战场大部分时间是"打完在等"。

### 方案

#### A. 电子战羁绊：换成「削输出」而不是「拖时间」

| 档位 | 现在 | 提案（激进） |
|---|---|---|
| 2 艘 | 敌方攻击间隔 +5% | 敌方**伤害 −10%** |
| 4 艘 | +10% | 敌方伤害 −18%，开火间隔 +5% |
| 6 艘 | +15% | 敌方伤害 −25%，开火间隔 +10% |

理由：
- 「伤害 −25%」等价于我等效血 +33%，比现在的 +7.5% 实打实强四倍多；
- 它**不依赖战斗时长**，TTK 缩短后收益不打折；
- 实现通道现成：`EveRunState.enemy_cycle_pct()` 已经证明"落到敌方"这条路走得通，
  照抄一份 `enemy_damage_pct()` 即可（`EveFleetFactory.build_enemy()` 里消费）。

⚠️ 25% 是激进值，可能过头。**建议先用 `sim_winrate` 跑 A/B 定档**，
不要照字面直接落表 —— 这个工程有现成的 120 局/格模拟，没必要靠感觉。

#### B. 电子战船自身：给一条"在场即削"的固有属性

现在它们纯亏数值、只贡献羁绊计数。建议给**所有电子战船**一条固有属性
（不靠羁绊，单艘就生效）：

> **干扰场**：本舰在场时，敌方全体开火间隔 +6%（多艘不叠加，取最大）

这样玩家"随手拿一艘电子战"就有体感，凑齐 6 艘才进大档。

#### C. TTK 缩短：三个杠杆，建议组合 ①+②

| 杠杆 | 做法 | TTK 影响 | 风险 |
|---|---|---|---|
| ① 提伤害 | 全局 `weapon_damage` ×1.2 | −17% | 一击秒杀感变强，小船更脆 |
| ② 降血量 | 全局 `max_hp` ×0.85 | −15% | 后勤/维修类价值下降 |
| ③ 缩时限 | 60s → 45s | 不变（只减少等待） | 等于把 TTK 压到时限边缘，超时判定变多 |

①+② 合计约 **39s → 27s**。⛔ 不建议单独用 ③ —— 它不缩短战斗，只是把"打得完"变成"打不完"。

落地位置：全局倍率要加在**唯一入口**，不能散落在 52 艘船表里。
`EveFleetFactory.build_own / build_enemy` 是天然的收口点（星级、羁绊都在那儿乘）。

#### D. 时限要不要跟着缩？

TTK 27s 的话，60s 时限就只剩 45% 利用率，建议 60 → **40s**，BOSS 70 → **50s**。
但这条会和「敌方编组难度」耦合（有些关卡靠磨），**建议 TTK 定档后再单独跑一轮胜率再定**。

## 四、装备系统

### 现状：只有壳，一件真装备都没有

| 层 | 状态 |
|---|---|
| UI | ✅ 有。`scripts/ui/panels/eve_equipment.gd`，8 格（2×4），能放能取 |
| 数据 | ❌ 无。item 只有 `{icon: StringName, color: Color}`，**没有 id、没有效果** |
| 状态 | ❌ 无。`EveRunState` 里没有装备槽，`set_slots()` 全工程**没有调用方** |
| 生效 | ❌ 无。没有任何代码把装备乘进 `EveShip` |
| 获取 | ❌ 无。事件 / 打捞 / BOSS 掉落都没接 |

⇒ 玩家永远看到 8 个空虚线框，**这就是"检查装备系统接口"的答案：接口是空的**。

### 好消息：挂载点全都预留好了

代码里散着三处注释，明确写着"装备将来改这里"：

| 字段 | 位置 | 语义 |
|---|---|---|
| `EveShip.shield_pierce` | `eve_ship.gd:208` | 护盾击穿率（0~1，战列舰现在 0.35） |
| `warhead_scale()` / `armor_scale()` | `eve_ship.gd` | 弹头 / 装甲倍率 |
| `weapon_damage` / `weapon_cycle` | `eve_ship.gd:148,146` | 直接改也行 |

### 接口设计（最小可用版）

**① 数据表** `scripts/data/eve_equipment_table.gd`

```gdscript
const ITEMS := {
    "warhead_rig": {
        "name": "弹头稳定器", "icon": &"warhead", "tier": 1,
        "apply": {"weapon_damage_pct": 0.15},          # 直接缩短 TTK
        "text": "伤害 +15%",
    },
    "piercer": {
        "name": "穿盾聚焦器", "icon": &"pierce", "tier": 2,
        "apply": {"shield_pierce_add": 0.25},          # 已有字段，直接可用
        "text": "护盾穿透 +25%",
    },
    "overclock": {
        "name": "超频循环", "icon": &"cycle", "tier": 2,
        "apply": {"weapon_cycle_pct": -0.12},          # 开火更快 = 更短 TTK
        "text": "开火间隔 −12%",
    },
}
```

**② 携带状态**（`EveRunState`）

```gdscript
var equipment: Array = []          # 长度 ≤ 8，元素 = 装备 id 或空
func equip_add(id: String) -> bool
func equip_remove(idx: int) -> String
```

**③ 生效时机** —— 两个选择，**建议快照式**

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 快照式（推荐） | `build_own()` 时把装备乘进 EveShip | 与星级/羁绊同一条管道，一次算完 | 战斗中途换装不生效（但战斗中本来也不能换） |
| 动态式 | 战斗中每帧查 `run.equipment` | 换装立刻生效 | 每帧开销 + 状态难解释 |

快照式的顺序要固定：**base → star → 羁绊 → 装备**（装备最后，因为它是最外层的玩家选择）。

**④ 获取途径**（建议三条，覆盖前中后期）

| 途径 | 节点 | 频率 |
|---|---|---|
| 事件节点选「拿装备」 | 现有事件表加一类 | 每 3~4 关一次 |
| BOSS 击杀必掉 | 节点 9 / 12 / 15 | 3 件/局 |
| 打捞残骸时有概率带装备 | 现有打捞系统 | 随机 |

**⑤ 装备槽 vs 舰船**：8 格是"背包"，不是"每船 8 格"。
玩家把装备**拖到某艘船上**才算生效 —— 拖放控制器现成（`EveDeployController`），
加一个 `equip_target` 来源即可。

### 装备与 TTK 的关系（回答玩家的第四条诉求）

玩家想用装备"缩短 TTK"是对的 —— **但装备是玩家侧的工具，不该拿来补系统的数值坑**。
如果靠装备才能把 TTK 压下去，那没凑到装备的局就是"又臭又长"。
⇒ 顺序应该是：**先做第三条的全局 TTK 调整（保证基线手感），再加装备（给玩家一个自己提速的把手）**。

## 建议的执行顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| 1 | 日志瘦身（②的 ①+②） | 最便宜、玩家感受最直接，半天能落地 |
| 2 | 通关演出 | 玩家明确的"这不行"，情绪价值最高 |
| 3 | TTK 全局调整 + 电子战改「削伤害」 | 要跑 `sim_winrate` 定档，最耗时 |
| 4 | 装备系统 | 依赖 3 的基线，否则数值没锚点 |
