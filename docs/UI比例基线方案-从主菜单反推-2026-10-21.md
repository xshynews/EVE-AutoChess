# UI 比例基线方案 · 从主菜单反推全站尺寸与字号（2026-10-21）

> **思路**（用户 2026-10-21 提出）：
> 先量主菜单各分区与按钮的**比例关系**，把这套比例当成全站基线，
> 再让其他页面的窗口尺寸、控件高、字号**按比例推导**，而不是各页各写一套常量。
>
> 本文只是**方案**，不改代码。拍板后再按 §7 分期落地。

---

## 1. 为什么这条路对

现状是「每页一套魔数」：

| 位置 | 写法 | 后果 |
| --- | --- | --- |
| 主菜单手机档 | `MOBILE_MODE_W=400` / `MOBILE_MODE_H=100` / 字号 `26` | 视觉基准（已真机验收） |
| HUD 顶条 | `MOBILE_TOP_H=64`、字号 `14 / 9` | 比主菜单小 1~2 档 ⇒ **「太小、不好点」的由来** |
| HUD 侧列 | `MOBILE_SIDE_W=242` | 13.6%W，主菜单同级是 22.4%W |
| 斗地主牌桌 | `BASE=1920×1080` 固定 + 自绘按钮 | 无手机档，圆角/字号自成一派 |
| 结算页 | 外框 `963×570`，内部无手机档 | 外框有、内容没跟上 |

⇒ 四套魔数之间没有任何约束关系，改一处不影响另一处，**必然长期漂移**。
比例基线的作用就是把它们绑到同一根尺子上。

## 3. 由此得到的三组刻度（建议成为全站唯一基线）

### 3.1 字号刻度 T（跟屏高走）

```
T1 = 0.0325 × H      # 800 → 26 · 864 → 28 · 1067 → 35
T2 = 0.0275 × H      # 800 → 22 · 864 → 24 · 1067 → 29
T3 = 0.0163 × H      # 800 → 13 · 864 → 14 · 1067 → 17
T4 = 0.0113 × H      # 800 →  9 · 864 → 10 · 1067 → 12
```

### 3.2 控件刻度 C（高度跟屏高、宽度看场景）

| 档 | 公式 | @H=800 | 用途 |
| --- | --- | --- | --- |
| **C1 主操作** | `0.125 × H` | **100** | 开始游戏 / 出牌 / 结算页主按钮 |
| **C2 系统按钮** | `0.090W × 0.1375H` | **160×110** | 设置 / 返回 等右上角入口 |
| **C3 行内次操作** | `0.070 × H` | **56** | 提示 / 托管 / 小按钮（≥48 ✓） |
| **C4 系统条（顶条）** | `0.080 × H` | **64** | HUD 顶条（沿用现值，不再加高） |

### 3.3 窗口刻度 W（宽度跟屏宽、内边距成对）

| 项 | 公式 | @1784×800 |
| --- | --- | --- |

## 5. 需要你拍板的三件事

### ① 侧列宽度：对齐主菜单，还是保战场？

| 选项 | 值 @1784 | 好处 | 代价 |
| --- | --- | --- | --- |
| A · 完全对齐主菜单 | **400 (22.4%W)** | 视觉最统一 | 左右各吃 400，战场只剩 984 宽 |
| B · 折中（**推荐**） | **321 (18%W)** | 明显变宽、仍留战场 | 比主菜单窄一档 |
| C · 不动 | 242 | 零风险 | 与主菜单始终差一档 |

### ② 顶条要不要也按 12.5%H 拔到 100？

- **推荐：不拔**。顶条是「系统条」不是「模式行」，保持 64（8%H），
  但把**字号**提到 T2/T3，让它「字变大、条不变高」。

### ③ HUD 战内字号能否接受 T2=22？

主菜单导语用 22 没问题，但顶条要塞 5 段内容。
**推荐：数值用 T2（22），标签用 T3（13）**，先在最窄档验证不换行再落地。

## 6. 落地方式（单一真相源）

新增 `scripts/ui/eve_ui_metrics.gd`（**纯静态函数**，无状态、无节点）：

```gdscript
static func t1(d: Vector2) -> int      # 0.0325 × H
static func t2(d: Vector2) -> int
static func t3(d: Vector2) -> int
static func c1_h(d: Vector2) -> float  # 0.125 × H
static func c3_h(d: Vector2) -> float  # 0.070 × H
static func c4_h(d: Vector2) -> float  # 0.080 × H
static func side_w(d: Vector2) -> float
static func edge(d: Vector2) -> float
```

**硬约束**：

1. ⛔ **桌面端一律返回旧常量**（`EveUiScale.is_mobile()` 为假时直通原值）
   ⇒ `verify_ui_scale` 第 3 段「桌面档位表 === `RECT_*`」继续成立。
2. ⛔ 不读 `size`，只吃传入的设计空间（与 `mobile_rects(d)` 同口径，可无头断言）。
3. ⛔ 不新增 i18n key。
4. 字号只经 `FONT.fs()`，⛔ 不直接 `add_theme_font_size_override`。

### ⚠️ 真机新发现（不在本期范围，需单独立项）

**主菜单「设置」窗：全屏窗 + 内容挤在左上角。**
- 现象：点设置后整屏变暗（那是全屏窗本身，符合「全屏页」设计），
  但窗内**栏目列 + 音频页只排在左上约 1/3 区域**，右侧与下方大片空白；
  「完成」按钮也在左上，未贴底。
- 量化：窗底色 (21,31,36) 铺满 2408×1080；内容实际只占左上约 1050×360。
- 判断：`_place_settings()` 手机分支按 `size` 铺满整屏是对的，
  ⇒ 问题在 **`EveSettings` 内部**：栏目布局/底栏没有跟随全屏尺寸重排（可能仍按 960×560 设计宽）。
- 影响：设置是全站入口，且手机上极易误以为「设置坏了」⇒ 建议列为**阶段 0-3 的替代优先项**。

**✅ 该问题已修（同日）**
- 根因：`EveWindow._content_host` 是**普通 Control**（不是 Container）⇒ 不会给孩子排版，
  `content` 永远停在自己的最小尺寸、贴左上。窗口≈内容最小尺寸时看不出来；
  一旦被铺成全屏（手机设置窗）就暴露。
- 修法：`_fit_content_to_host()` —— **仅手机端**把 content 铺满宿主；桌面端直接 return（守逐像素不变）。
- 回归断言：`verify_window` [7] 三条（手机铺满 / 桌面仍是最小宽度），套件 41 → **44/0**。
- 真机复验：滑杆铺满整宽、底栏「恢复默认设置 / 完成」贴底，`outputs/android_shots/s10_settings.png`。

⚠️ 每期结束都要跑 `tools/run_verifies.sh`，**失败计数 > 0 即失败**。
